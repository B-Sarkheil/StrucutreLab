# Structure Lab

Integrated engineering desktop software for Windows (Python + PySide6) for about 30 users. It gradually replaces scattered MATLAB and Excel-VBA tools. Each tool is a plugin.

First real tool: **Auto Design**, automatic structural section optimization (Genetic Algorithm + SAP2000 OAPI). Development resumed on 2026-10-27: it is **enabled** (`AUTO_DESIGN_ENABLED = True` in `plugins/registry.py`). Its wizard has five input pages (file, sections, frame types, constraint settings, GA settings), a live run page and, since 2026-11-04, the typing page of the final member (step 10). The run executes GA steps 5 to 9 with a real `fitness_calculator` (weight W and constraint violation CV). Two constraints exist: the **stress ratio** of every frame and, since 2026-11-09, the **beam deflection** (relative to the chord, computed from the moment diagram; see "Beam deflection constraint"). Step 10 (typing / standardizing the sections of the selected member, saved as a new SAP2000 file) is written; the step after it is not described yet (see "Auto Design"). Second tool: **SLD to SAP**, loading the SAP2000 model from piping SLD files exported from AutoCAD.

Design context lives in these docs in the project knowledge:

* `claude/engineering-platform-decisions.md`: bootstrap / runtime / app layers, auto-update from the server, IT constraints.
* `docs/contract.md`: the frozen contract between the launcher and the app (layout on the user machine, server share, update rules, the update question).
* `claude/project-plan-structural-optimization.md`: Auto Design plan (Phase 1 GA, Phase 2 ML surrogate lab, Phase 3 general model). Written in Persian. Key rules: the GA only calls `evaluate(x)`; save every evaluation from day one (training data for the ML phase); the final answer is always confirmed with the real engine; ML never becomes a dependency of the GA.
* `docs/sld_to_sap_algorithm.md`: the SLD to SAP algorithm guide. The code is the reference; if they disagree, the guide must be fixed (or, after a decision, the code).
* A complete document of the implemented Auto Design algorithm will be written at the end of the work (planned, `docs/` folder; not created yet). Until then the user describes the GA to Claude step by step, and this README only keeps what is needed to continue the work.

## How the app works

* `__main__.main()`: `setup_logging()` → QApplication → `apply_theme` → `register_builtin_plugins()` → `MainWindow` → 300 ms later `MainWindow.show_release_notes_if_needed()` → `app.exec()`.
* **Plugin contract** (`plugins/base.py`): `name` (unique key), `title`, `icon`, `description`, `available` (False = planned, not built), and `create_widget() -> QWidget`.
* **Registry** (`plugins/registry.py`): explicit and simple. `register_builtin_plugins()` lists all plugins in navigation order (Auto Design, SLD to SAP, PDMS to SAP, Auto CPS); `load_plugins()` returns them. No auto-discovery yet. **Release switch:** `AUTO_DESIGN_ENABLED` (currently `True`): the real `AutoDesignPlugin` is registered. When set to `False`, Auto Design is registered as a `PlaceholderPlugin` with the same name, title, icon and description, so it appears in the sidebar and on Home as a planned tool and opens the "Under development" page. The switch stays in the code to hide the tool again if needed (for example during a long development pause).
* **Shell** (`ui/`): `MainWindow` reads the registry and passes the plugins to `Navigation` (sidebar) and `HomePage`. Clicking a sidebar item or a card calls `MainWindow.show_page(key)`. Home is built at startup; each plugin page is created lazily on first open and kept in a `FadeStackedWidget` (a `QStackedWidget` that fades the new page in). If `create_widget()` fails, the error is logged and the current page stays. The About page is a shell page (not a plugin) opened from the About card at the bottom of the sidebar.
* **Home page caveat:** `home_page.py` has a fixed list `plugin_order = ["auto_design", "sld_to_sap", "pdms_to_sap", "auto_cps"]`; only plugins named there get a card or row. A new plugin must be added to that list until it is replaced by the registry order (see known issues).
* **Not implemented yet (shown as planned, open the "Under development" page):** Auto CPS and PDMS to SAP.
* **Visual language** ("structural drawing sheet"): all colors are tokens at the top of `ui/theme.py` (blueprint-ink surfaces, drafting-cyan linework, amber as the single signal color for active/hover/focus, plus `BLUE`, `DANGER`, `PAPER`, `STEEL`, `STEEL_DIM`, `RULE`, `RULE_HI`, `INK*`). Titles use Bahnschrift, body uses Segoe UI. Most widgets are styled by `objectName` in the stylesheet; cards, the hero banner and the sidebar marker are painted in code (`ui/widgets.py`, `ui/home_page.py`, `ui/navigation.py`) and read the same tokens. Available tools get large cards, planned tools get dashed rows. The hero banner fades its logo in once over 5 s (`HeroBanner.FADE_MS`), which is the only unprompted motion in the app; the About page logo emblem spins while visible. `ui/loading_overlay.py` is the shared loading overlay (delay 200 ms, minimum visible 450 ms, blocks input to the page below). New pages of a plugin follow the same look (see `run_page.py` for a page that paints its own widgets with these tokens).
* **Small modal windows** (`ui/sheet_dialog.py`): "What's new" and "Update available" are frameless dialogs drawn on the About page's `SheetCard` (same blueprint grid and corner marks). `SheetDialog` is the base (heading, divider, buttons, scrollable list of framed version cards that grows up to 300 px, drag by any free area, indeterminate `BusyBar` drawn in code); `ReleaseNotesDialog` and `UpdatePromptDialog` only fill it.

## Release notes

* **Source:** `src/release_notes.json`, written by hand for every release: `{"releases": [{"version", "date", "title", "items": [{"tag": "new|improved|fixed", "text"}]}]}`. An item may also be a plain string (tag `improved`). Entries without a version or without items are ignored. Write what a *user* needs to know, not the code changes (those go to the README change log). A version without an entry has no window.
* **After an update** (`core/release_notes.py`, `MainWindow.show_release_notes_if_needed()`): the last version whose notes the user has seen is stored in `<data dir>\user_state.json` (`last_seen_version`; not `state.json`, which belongs to the launcher). If `__version__` is higher, the notes of every version in between (newest first) open in `ReleaseNotesDialog`; **Got it** closes it and the version is stored. A fresh install shows nothing (the current version is just stored). The stored version never goes backwards (rollback safe). A broken notes file or any error shows nothing and never blocks the app.
* **Not in the update window:** the notes are shown once, after the update, in "What's new"; the update window only shows the two versions and the question. `build.py` still copies the newest 10 entries into `latest.json` (`release_notes`) and the launcher passes them to `ask_update()`, which ignores them for now (kept for a possible later use).
* **Look:** each version is a framed card titled with its version and date; the item tags are NEW (green), IMPROVED (blue) and FIXED (warm); colors are defined in `ui/sheet_dialog.py` (`TAG_STYLES`).

## Release and update system (done, first release 1.1.5 installed and started on the user's PC; update question added in launcher 1.1.0)

Three layers (details and frozen rules in `docs/contract.md`). Installed copy: `%LocalAppData%\Structure Lab\` (with a space; `core/paths.py` has `APP_NAME = "Structure Lab"` and uses `STRUCTURELAB_ROOT` when the launcher sets it).

* **Installer** (`bootstrap/installer.iss`, Inno Setup 6 or 7): per-user, no admin rights, silent mode `/VERYSILENT`, no entry in Programs and Features (`Uninstallable=no`). Copies bootstrap (small Python + `launcher.py` + `initial.json`), the first runtime and the first app version, plus `settings.json` (server path; never overwritten by a re-install). Start Menu shortcut (and optional desktop) runs `bootstrap\python\pythonw.exe bootstrap\launcher.py`, with `AppUserModelID` `StructureLab.App` and the icon `app.ico`. The Setup.exe is given to users once; it is **not** part of the server folder.
* **Launcher** (`bootstrap/launcher.py`, `BOOTSTRAP_VERSION = "1.1.0"`, standard library only): on every start reads `latest.json` from the server share with a 5 s timeout (unreachable server: skip, start the installed version). If the server app version is higher (and not rejected before) it **asks the user**: it starts the installed app with `ask_update()` (`python.exe`, no console window), which shows the "Update available" window (installed version in the warm color → new version in cyan, the question, **Update now** / **Later**; for a mandatory update **Update now** / **Exit** and Esc is ignored) and prints `UPDATE`, `LATER` or `EXIT` on stdout. `LATER` starts the installed version (asked again next start); `EXIT` ends without starting; `UPDATE` switches the same window to "Updating…" while the launcher downloads the needed zips to `tmp\`, checks sha256, extracts beside the target, renames atomically, runs the self-check (`ping_app()` with the new runtime and the new app), switches `state.json` and then terminates the window. A failed self-check deletes the new folders and records the version in `rejected`; if any update step fails the installed version starts (even when mandatory). If the window cannot run (an old app without `ask_update`, a crash, no display) a plain Windows message box asks instead (Yes/No; mandatory: information, then update). No question is asked when the installed version is missing or damaged (repaired directly) or with `--update-only` / `--yes` (IT scripts). Keeps only the current and the previous app/runtime. A lock file prevents two instances updating at once. The app runs as a child process with the runtime's `pythonw.exe`; if it exits within 6 s a message box is shown. The update never restarts a running app: the new version starts at the next launch.
* **Logs** are local only: `%LocalAppData%\Structure Lab\logs\` (`launcher.log` for updates, `app.log` for the app, `app_stderr.log` and `update_prompt_stderr.log` for startup errors). `core/logging_setup.append_server_log` is an unused stub; `core/config.Settings` only has `server_dir` and `channel` (the contract's `network_timeout_sec` is read by the launcher, not by the app).
* **Server share:** `\\be-sarkheil\Share\Structure Lab` (read access for users). Holds `latest.json`, `app-<version>.zip`, `runtime-<id>.zip`. Old zips stay there (publish.py never deletes); only the ones in `latest.json` are needed.
* **`tools/build.py`:** reads the version from `src/version.py` (stops if `pyproject.toml` shows another one), zips all files under `src/`, builds the runtime zip from `runtime/python` only when the runtime id changes (id = hash of `runtime/requirements.txt` + Python DLL name; dev packages, `Scripts/` and `__pycache__` are left out; the dev `python312._pth` with `..\..` is replaced by a clean one), writes `latest.json` last. `latest.json` also carries `release_notes` (newest 10 entries of `src/release_notes.json`; a warning is printed when there is no entry for the version being built) and, with `--mandatory`, `"mandatory": true`. With `--installer` it also builds `dist\stage` and `dist\StructureLab-Setup.exe` (ISCC is found in the usual Inno Setup 6/7 folders or with `--iscc`).
* **`tools/publish.py`:** copies the zips from `dist\publish` to the server (skips files that are already there), `latest.json` last.
* **`min_bootstrap_version`** in `release_config.json` is the version of the *launcher* (`BOOTSTRAP_VERSION`), not of the app. It is now `1.1.0`. Change it only when `launcher.py` changes and a new Setup is required (users with an older launcher are then told once to ask IT).

How to release a new version (e.g. 1.2.1), no new Setup needed:

1. Change the code and test. 2. Set the new version in `src/version.py` (and `pyproject.toml` unless it reads the version from `version.py`); set `__release_date__` too. 3. Add the entry of the new version to `src/release_notes.json`. 4. `.\runtime\python\python.exe tools\build.py` (add `--mandatory` when users must not postpone it) 5. `.\runtime\python\python.exe tools\publish.py`. Users are asked at their next launch. A rejected version is not retried: publish a higher version to fix it. Going back means re-publishing the old code with a higher number. A mandatory flag applies to the newest version on the server only: a user who is several versions behind is forced only if the newest one is mandatory.

First release / new Setup: `.\runtime\python\python.exe tools\build.py --installer [--iscc "<path>\ISCC.exe"]`, then `publish.py`, then hand `dist\StructureLab-Setup.exe` to the users. If you add a library, install it into `runtime\python` first (`pip install -r runtime\requirements.txt`); the runtime id changes and users download the new runtime once. **Launcher 1.1.0 (the update question) reaches a PC only through a new Setup**; until then that PC still updates silently (launcher 1.0.0 stops updating once `min_bootstrap_version` is 1.1.0 and tells the user to ask IT).

## Auto Design (current state; enabled, see the release switch)

A wizard inside the plugin (`ui/wizard.py`, a `QStackedWidget`); the shell knows nothing about its steps. Field names are camelCase on purpose (`popSize`, `frameSections`, `materialType` ...), the same name from the form down to the GA code.

### The steps of the algorithm and what exists

The user described the algorithm to Claude a few steps at a time. The "20 steps" he mentioned (`TOTAL_STEPS = 20` in `ga_run.py`) **count the sub-steps too** (clarified on 2026-11-02): steps 1 to 9 with all their sub-steps are the GA part, and they are written. **Step 10** (typing of the selected member) was described and written on 2026-11-04. The user said that **another step comes after step 10**; it is not described yet. Do not invent steps that the user has not described.

**Numbering rule (agreed with the user on 2026-11-03, step 4 split into 4.1 and 4.2 when the constraint settings page was added):**

* Steps **1 to 4 are the wizard pages**: 1 reference file, 2 allowed sections ("Is Allowed" table), 3 frame types, **4.1 constraint settings, 4.2 GA settings**. The **Simulate Evolution button belongs to step 4.2** (it confirms the database folder and starts the run); it is not a step of its own.
* Steps **5 to 9 are the run**, in the code `step5_...` to `step9_...` of `ga_run.py` (5 Material Types, 6 frame sections, 7 geometry, 8 initial population, 9 generation loop). The sub-steps are written with dots (`9.1.3`, `9.2`) in the comments.
* **Step 10** is the last page of the wizard: the run page gets a **Next** button (enabled after the run finished) and the typing page (`ui/typing_page.py`) follows. It is not part of `run_ga`; it works on the finished run (`wizard.context`).
* The frame types (the role of every frame, `classify_frame`) were first a sub-step inside step 8; since 2026-11-03 they are **step 3**, decided once on their own page. Step 8 only reads `ctx.frameRoles`.
* `TOTAL_STEPS = 20` and `FIRST_RUN_STEP = 5` in `ga_run.py` are left over from the old progress estimate (see "Known technical issues"); they are not the step numbers.
* Every module and function that belongs to a step names it in its docstring (`step 3`, `step 8`, ...). Keep the numbers in the docstrings, in the log lines (`Step 5 - ...`) and in this table the same.
* **Generation numbering (agreed with the user on 2026-11-04):** `genSize` is the **number of generations**. Generation 1 is the initial population (step 8, outside the loop); step 9 builds generations 2 .. `genSize`, so its loop runs `genSize - 1` times. The run page, the chart and the folders on disk all use the same numbers: chart point `k` = folder `Generation-k`.

* State: `sap_path`, `sections`, `frame_roles` (from step 3), `constraints` (step 4.1), `params` (step 4.2), `sap` (the live `SapClient`, taken from the sections page), `context` (the last finished run), `_run_context`, `_run_worker`, `_typing_page` (step 10). * **Simulate Evolution** → `_on_params_accepted` → `_confirm_database_folder`: `check_folder_usable` (refuses a drive root, the user's home folder, a file, or a folder that contains the reference file) and, when the folder is not empty, a Yes/No warning (default No) that **everything inside will be permanently deleted** → `_start_run`.

* **Cancel** is cooperative (`services/run_monitor.py`): `RunMonitor.cancel()` sets a flag; `monitor.status(...)` is a checkpoint that raises `RunCancelled` (step 9.2 also calls `raise_if_cancelled()` between the copies); a SAP2000 call already running cannot be interrupted. The run page confirms Cancel with a dialog and allows Back only after the run stopped.
* **Progress** is real and counted in members: `ctx.totalMembers = N * genSize` (N members of generation 1 plus N children in each of the `genSize - 1` iterations) and `ctx.doneMembers`. `ga_run._member_done` is called after every `fitness_calculator` call (the reference member in step 8 and every member built by `_make_member`) and reports `doneMembers / totalMembers`. `prepare_database_folder` and steps 5 to 7 are not counted (they are fast); the copies of step 9.2 are not counted either, so the bar stops near 99 % until the run page sets 100 % on `FINISHED`. `TOTAL_STEPS` and `FIRST_RUN_STEP` in `ga_run.py` are no longer used for progress and can be removed.

To add an objective add a `MetricSpec` and the value in `GenerationStats`. **DCR always means the stress ratio, never the governing ratio** (agreed with the user on 2026-11-09): the governing ratio (max of stress and deflection) is used only inside `fitness_calculator` to build CV and is not shown anywhere. It is fed by `start`, `add_status`, `set_progress`, `add_generation`, `set_final`, `set_state`. ### Run start: database folder (`prepare_database_folder`, `services/database_folder.py`)

At the start of `run_ga` (before step 5) the run re-checks the folder, **opens the reference model first** (so SAP2000 does not hold the files of a previous run; the reference is outside the folder), then deletes everything inside `modelsFolder` (the folder itself stays). ### Step 8: initial population (decided with the user)

* Population size is always **even**: `N = popSize + popSize % 2` (members are paired later). The reference model is member 1; the loop `i = 1 .. N-1` builds the others.
* Folder layout (one `Generation-<g>` per generation, member folders inside, each with the SAP file of the same name):

  ```text
  <modelsFolder>\Generation-1\Gen-1-1\Gen-1-1.sdb       copy of the reference file
  <modelsFolder>\Generation-1\Gen-1-2\Gen-1-2.sdb       ... up to Gen-1-N (the parents)
  <modelsFolder>\Generation-1\Gen-1-(N+1) ... Gen-1-2N  children of iteration g = 1 (step 9.1)
  <modelsFolder>\Generation-2\Gen-2-1\Gen-2-1.sdb       the best N of the 2N (step 9.2) ... up to Gen-2-N
  ...
  <modelsFolder>\Generation-<genSize>\                  final population (best N; it has no children of its own)
  ```
* **Gene = one frame** (not a section group). Genes are independent; the same section may appear in many genes. A random section for a frame is chosen from the sections that have **the same Material Type as the frame's reference section** and are **allowed for the frame's role** (column, beam, horizontalBrace, verticalBrace; the role comes from `ctx.frameRoles`, step 3). The options are computed once before any folder is made (`build_gene_options`); a frame with no Material Type, no role or no allowed section stops the run at the start with all problems listed together.
* After the check of the roles, step 8 builds `ctx.deflection` (`_deflection_settings`): the deflection combination and the divisor of step 4.1 and the tuple of frames whose role is Beam. No combination chosen, or no beam in the model → None (a warning for the second case).
* Member i is built by `ga_run._make_member` (shared with step 9): open the reference model, `unlock_model`, assign the new section only to frames whose section differs from the reference, `save_model_as` the member's path, then `fitness_calculator(sap, path, deflection=ctx.deflection)`. The reference model is reopened every time (clean start, no old results). The reference member itself is evaluated too, on its **copy** `Gen-1-1.sdb`, and its fitness is kept in `ctx.referenceFitness`.

### Fitness: weight W and constraint violation CV (`services/fitness.py`, `services/design_results.py`, `services/deflection.py`)

`fitness_calculator(sap, path, weights=None, deflection=None)` works on the open (already saved) model and returns a `Fitness` (`weight`, `cv`, `elementViolation`, `globalViolations`, `meanRatio`, `maxRatio`, `elementCount`, `meanDeflection`, `maxDeflection`, `deflectionCount`):

1. With `deflection` set (and at least one beam): `unlock_model()` and `set_output_stations(beam, 20)` for every beam (see the deflection section).
2. `run_analysis()` (an error stops the run), `run_steel_design()`, `run_concrete_design()` (a non-zero code only gives a log warning; a model without concrete gives the warning "Concrete design returned an error code" at every member, which is normal). The **design combinations of the file are never touched**: whatever the user selected as Design Combos is used.
3. **W** = sum of the column `TotalWeight` of the table `Material List 1 - By Object Type` (kg). The table has no total row (confirmed by the user).
4. **Stress ratio of every frame** (API calls with item type Group and name `ALL`, so the design code name never matters): steel `DesignSteel.GetSummaryResults` (`Ratio`); concrete columns `DesignConcrete.GetSummaryResultsColumn` (`PMMRatio`); concrete beams `DesignConcrete.GetSummaryResultsBeam` (no DCR exists: a beam with an error message gets the fixed ratio `ERROR_RATIO = 1.5`, strict on purpose, otherwise 0). A steel frame or concrete column with an error message gets at least 1.5 too. If no frame was designed at all the run stops with a clear error. A call that returns a non-zero code (for example no concrete in the model) counts as nothing of that kind (log warning).
5. **Deflection ratio of every beam**: `read_deflection_ratios` (below), merged with the stress ratios by the max per frame (`governing_ratios`).
6. The model is saved again at the end, so the `.sdb` that is copied to the next generation keeps the analysis and design results.

CV (decided with the user, 2026-11-09):

```text
r_i_gov = max(stress ratio, deflection ratio)   governing ratio of element i (a beam has both, other frames only stress)
v_e     = mean_i max(0, r_i_gov - 1)            over ALL frames with a ratio
v_d     = mean_j max(0, r_j_drift - 1)          global constraints (drift later; none now)
CV      = w_e * v_e + w_d * v_d (+ ...)         w_e = w_d = 1 for now (CvWeights)
```

A single violating frame makes CV above 0 and so puts the member in the second group of the ranking; the small weight of one frame in the mean does not matter because every member with CV = 0 is taken first (the user's remark, accepted: do not change the denominator).

What is shown to the user is **not** the governing ratio: `meanRatio`, `maxRatio` and `elementCount` are the **stress** ratios of all designed frames; `meanDeflection`, `maxDeflection` and `deflectionCount` are the deflection ratios of the beams (0 when the constraint is off).

To add a constraint: an element constraint is a reader `f(sap) -> {frame: ratio}` whose result is added to the list given to `governing_ratios` in `fitness_calculator` (the old `ELEMENT_CONSTRAINTS` tuple was removed on 2026-11-09); a global constraint is a reader `f(sap) -> [ratio, ...]` added to `GLOBAL_CONSTRAINTS` under a name, with its weight in `CvWeights.globalWeights`. Drift will need `Setup.SetComboSelectedForOutput` (combos for analysis output); that must still be discussed with the user because it touches the output selection of the file (the deflection constraint already does that, see below).

**Ranking** (`ranking_key`): a member with `CV <= CV_EPSILON` (1e-6) is feasible. Feasible members come first ordered by W (smaller is better), then the infeasible ones ordered by CV (smaller is better). The key is `(0, W)` or `(1, CV)`; a **smaller key is a better member**. The operators in `genetic_operators.py` take a function `rank(individual)` and sort ascending; the same rule is used by the tournament (the best two of the drawn members) and by step 9.2 (the best N of the 2N).

### Beam deflection constraint (`services/deflection.py`; written 2026-11-09, works with an Envelope combination on the user's test model)

* **Input:** the combination and `L / n` chosen on step 4.1 (`DeflectionSettings.combo`, `divisor`), one limit for all beams. Only frames of role **Beam** are checked (the user: columns and braces have no meaning here).
* **Ratio:** `ratio = (max |w_rel| / L) * n`, where `w_rel` is the deflection **relative to the chord** in the principal direction (local axis 2, moment `M3`). 1.0 is exactly the allowed deflection, the same scale as the stress DCR. The absolute end displacements (`JointDispl`) are **not** needed: with `w(0) = w(L) = 0` the relative deflection depends only on the moment diagram.
* **Method:** the moments at the output stations (`AnalysisResults.FrameForce`, `M3`) are taken as piecewise linear, the curvature `M/EI` is integrated twice (trapezoids) and the straight line joining the two ends is removed (`relative_deflection`, pure numerics). `EI = E · I33 · (I33 modifier of the section) · (I33 modifier assigned to the frame)`, constant along the beam, **shear deformation ignored**. `E` from `Material Properties 02 - Basic Mechanical Properties` (`E1`), `I33` from `Frame Section Properties 01 - General`, the modifiers from `PropFrame.GetModifiers` and `FrameObj.GetModifiers` (8 values, `I33` is index 5; a failed call gives 1.0). The beam's section is the one of the **current** model.
* **Output stations:** `FrameObj.SetOutputStations(frame, 2, 0.0, 20, False, False, Objects)` before the analysis: `MyType = 2` is taken as "minimum number of segments", so at least 20 segments (21 stations); point loads still get their own station. This needs the model unlocked and is saved in the file of every member.
* **Combination expansion** (`expand_combination`): the API has **no call for the type of a combination** (`RespCombo.GetTypeCombo` does not exist; the first version failed because of it). An Envelope (or anything that gives Max / Min rows) is found from the results: the combination is selected alone for output and `FrameForce` of the first beam is read; if StepType is Max / Min it is opened with `RespCombo.GetCaseList` into its members (recursively when a member is a combination). Every non-envelope combination and every load case found this way is selected for output, the deflection is computed for each one separately and the **largest ratio** is kept. Rows that still have Max / Min (response spectrum, moving load, an envelope that could not be opened) are skipped with a warning and the run **goes on** (the user's decision). The same warning text is logged only once per run (`DeflectionSettings.warned`). If **no** beam gets any usable result the run stops with `SapError("No usable deflection result ...")`, because a silent 0 would switch the constraint off. Range Add / Absolute Add combinations are treated like the others (the user: the user decides which combinations are right, Claude only computes). The combination should be a service (unfactored) combination; that is the user's responsibility.
* **Side effect on the files:** the output selection of the model is changed (`DeselectAllCasesAndCombosForOutput`, then only the deflection combinations / cases are selected) and kept in the file of every member. The Design Combos are never touched.
* **Known limits:** a beam rotated about its own axis (local axis 2 not vertical) is not handled; a **cantilever** gets the same relative-to-chord rule (not meaningful there; no separate limit); the beam's section is read from the model every time and `section_i33_modifier` is not cached (add a cache by section name if it is slow).
* **Warnings are only in `app.log`** (`Deflection: ...`), not on the run page.

### Step 9: generation loop (decided with the user, written)

Loop `g = 1 .. genSize - 1` (`genSize - 1` iterations; iteration g builds generation g + 1). Pure operators are in `services/genetic_operators.py` (no SAP), the loop is `ga_run.step9_generations`. The DNA of a member is its genes in the order of `ctx.frameSections` (SAP table order).

* **9.1** Loop `m = 1 .. N/2` (`0.5*(popSize + mod(popSize,2))` pairs). Per pair:
    * 9.1.1 / 9.1.2 **Tournament** (`tournament_parents`): `tournamentSize` **different** members are drawn at random from the population; the two with the best rank are the parents (ties: the first drawn). `tournamentSize` must be at least 2 (and at most the population size).
    * 9.1.3 **Cut points** (`random_cut_points`): three different random numbers between 1 and the number of genes (frames), sorted. Cut `c` means genes `1..c` stay before the cut. If `c3` equals the number of genes the fourth part is empty and the crossover is in fact two-point; this is allowed and does not fail. At least 3 genes are required (clear error otherwise).
    * 9.1.4 **Three-point crossover** (`three_point_crossover`): both parents are cut into four parts and parts 2 and 4 are exchanged: child 1 = `A1 B2 A3 B4`, child 2 = `B1 A2 B3 A4`.
    * 9.1.5 Both children are built and evaluated with `_make_member` **inside Generation-g**, next to their parents, as members `N+1 .. 2N` (`Gen-g-(N+1)` ... `Gen-g-2N`), so `Generation-g` holds 2N members.
* **9.2** (`_step9_2_next_generation`) The N best members (by `ranking_key`) among the 2N (parents first, so a parent wins a tie) are **copied** to `Generation-(g+1)` as `Gen-(g+1)-1 ... Gen-(g+1)-N`, best first, and become `ctx.population` for the next iteration (genes and fitness are carried over, nothing is re-evaluated). **Only the `.sdb` is copied** (`database_folder.copy_member_model`; it keeps the analysis and design results), the originals stay in `Generation-g`. Before copying, the reference model is reopened so SAP2000 does not lock the last evaluated file. There is **no Dominated folder** (an idea dropped on 2026-11-02). After 9.2, `_report_generation(ctx, g + 1)` feeds the run page.
* After the last iteration `Generation-<genSize>` holds the final population and its best member is the one step 10 works on (`best_individual`). With `genSize = 1` the loop does not run and the initial population is the final one.
* Disk: every generation keeps all its member folders with the files SAP2000 wrote while running; the size grows with `genSize * popSize`.

### Step 10: typing (standardizing) of the final member (decided with the user 2026-11-04, written; its tiles were seen on a real run on 2026-11-09)

**Flow.** After the run reaches 100 % (state FINISHED) the Next button of the run page is enabled; the run page shows the card of the selected member (name, weight, max DCR, max Deflection, path of its `.sdb`). Next opens the typing page (`ui/typing_page.py`, `TypingPage(ctx, best)`; Back returns to the run page).

**Typing page.** Top: **four tiles** (the `StatTile` of the run page): *Weight* (kg), *Mean DCR* (the stress ratio of the frames of the selected structure, "max ..." below, green up to 1.0 and red above), *Mean Deflection* (same layout for the beams; "–  not used" when the constraint is off) and *Weight vs reference* (`weight_change_percent`, from `ctx.referenceFitness`; green when negative). The two ratio tiles are exactly the same as the boxes of the run page. A red line is shown when the member is still infeasible (CV above `CV_EPSILON`). Below: the table, as **one framed group per type, in the order Column, Beam, Vertical Brace, Horizontal Brace** (`TYPING_ORDER`), each group with the color of its type (`ROLE_COLORS` of `roles_page.py`). Columns: **Type** (name, number of frames and of sections), **Section** (one section per row; only the sections the member really uses; sorted by name, natural order), **No.** (number of frames with that section), **Number of types** (one input per group, spanning its rows). A type with no frames shows "not used" and no input.

**Number of types input** (`TypeCountEdit`): a text box plus ▲ / ▼ buttons (also the Up / Down keys); whole numbers only, from 1 to the **number of different sections of that group** (more types than sections makes no sense; the user wrote "real numbers above 1", this reading is the assumption: remove the maximum in `_GroupCard` if it is not wanted). An empty or out-of-range text is restored when editing ends. `TypingPage.typeCounts` gives role → number of types.

**Typify Sections button** (bottom centre, text in `TypingPage.BUTTON_TEXT`, icon `typify.png` with a drawn I-section as fallback). It can be pressed any number of times (change the numbers, press again). Each press:

1. First press only: a worker thread (`_AreaLoader`) opens the final member and reads the area of every section (`services/section_areas.py`, table `Frame Section Properties 01 - General`, field `Area`, m²). The areas are cached for the page.
2. `typify_member` (`services/typify_sections.py`) runs `typify` for every type separately with the lengths of the frames (from the joint coordinates, `math.dist`), the areas and the Material Types. The page shows the result card: frames changed, and the weight increase of every type and of all frames in percent (the extra volume over the original volume of the frames, independent of density; with mixed materials it is approximate).
3. A Save dialog (default `<reference name>_Typified.sdb` next to the reference file). The reference file and the final member's own file cannot be chosen (a warning asks for another name). Cancelling the dialog saves nothing; the result stays on the page.
4. A worker thread (`_ModelWriter`) assigns the new section to every frame that changed in the model that is already open (the final member, opened once by `_AreaLoader`; later presses only assign the differences from the previous typified model) and `save_model_as` the chosen path. The final member's file and the reference are never modified. If a save fails the state is unknown and the next press opens the final member again. **The saved model is not analyzed again** (the page says so); the new ratios need a new analysis and design (see "Next session").

**The algorithm** (`typify`, the user's own code `typify_sections.py`, reviewed 2026-11-04 and found correct): sections of one group are merged by name (lengths added), sorted by area, and split by dynamic programming (O(K·n²)) into at most K contiguous ranges; every section of a range is replaced by the largest one of the range (the cheapest replacement that is allowed for all of them); the result is the optimal least extra weight. Assumptions: a bigger area is an allowed replacement (not guaranteed for capacity: shapes and axes differ, which is why a new analysis is needed) and weight is proportional to area × length. **Extension made by Claude:** the items are sorted by (material, area) and a range may not mix materials (infinite cost), so a concrete section is never merged with a steel one; if K is smaller than the number of materials of the group a clear error is shown. Comments and messages were translated to English at the user's request. Typify does not look at deflection: a bigger area is not always a bigger `I33`; the new ratios need a new analysis.

## SLD to SAP (current state)

Converts the piping SLD (CSV files written by `SLD2SAP.lsp` from the AutoCAD layer `TAGGED_LOADS`) into two SAP2000 import tables: joints (point loads, circles) and distributed frame loads (rectangles). It is a port of the user's working MATLAB tool `SLD2SAP.m` (v1.4). The full algorithm, file formats, token table, error codes and the verified differences from MATLAB are in `docs/sld_to_sap_algorithm.md`; this section only describes the code.

* **Inputs** (`ui/page.py`): `z0` (m, default 0), tolerance (mm, default 10), end tolerance (mm, default 5), EQ.Z coefficient (**default 1**, also the default of `SldParams.eqz_coef`), friction coefficient (default 0.15); a list of CSV files or folders; the SAP2000 Excel export (sheets `Connectivity - Frame` and `Joint Coordinates`). The output folder is asked in a dialog when **Convert** is pressed (the dialog starts next to the Excel file); existing output files with the same names are overwritten without asking. `LISP` is not changed.
* **Downloads on the page:** "Download LISP" saves `assets/SLD2SAP.lsp`; "Open Rules" opens `assets/Rules of SLD2SAP.pdf` from a copy in the temp folder (so a PDF viewer never locks a file inside the app folder and blocks updates).
* **All problems are shown together, automatically.** Any change of an input (file added or removed, Excel file, any parameter) re-runs the whole check in a background worker (debounced 350 ms; older results are dropped by a version counter; the loading overlay appears only if it takes longer than a moment). Without a valid Excel file only the structure check (`check_structure`, CSV files only, S codes) runs; with it, `convert` also adds the matching errors (M codes). The Excel file is read once and cached by (path, modification time, size). Nothing stops at the first error.
* **All or nothing:** `Convert` is enabled only when the full check has no error, and `write_outputs` refuses to write when the result has errors. Warnings (W01: two points with the same coordinates) do not block. Convert runs `convert` again (the Excel comes from the cache) before writing.
* **Issue table:** sorted by file, then errors before warnings, then `Index`. Double-clicking a row copies its CAD coordinates (mm) to find the object in AutoCAD.
* **Outputs:** `SAP2000 Joint Coordinates.xlsx` (sheet `Joint Coordinates`) and `SAP2000 Distributed Loads.xlsx` (sheet `Frame Loads - Distributed`), written from row 4 into the workbooks in `templates/`. Headers are fixed SAP strings and must not be changed. `relDist` / `absDist` are not rounded (bit-for-bit comparison with MATLAB is the goal). Frame names are written as numbers only when they are a canonical integer string (`9`, not `007`), else as text.
* **Behaviours that differ from MATLAB on purpose** (all confirmed in the guide): the "load inside the frame" test is correct for reversed frames (`lo = min(pI,pJ)`, `hi = max(pI,pJ)`), `endTolerance` is applied at the beam ends and the distances are clamped to `[0, Length]`, point names must be unique over all files (S10), `LS`/`LT` duplicates are checked in plans, a non-numeric value after `=` (S14) and a text that is only a number (S15) are errors, halves are rounded away from zero (`round_mm`), point names are compared case-insensitively (SAP is not case sensitive), a negative load value is an error (S18), `V=`/`FV=` twice in one rectangle is S11, a non-numeric `Index` is S17, a CSV with no data rows is S01, a frame with a non-positive `Length` is M06 and a joint with non-numeric coordinates is M07. When the Connectivity file is unusable (M03/M04) no frame matching runs, so there is no flood of M01. `check_structure` takes `z0` so W01 in stage 1 uses the user's value (`ui/page.py` passes `self.params.z0`).
* **Not implemented:** warning W02 (file name does not match the origin row), plan rectangles that are not axis-aligned (never produced by the current LISP), graphical preview (declined), direct import into SAP2000 through OAPI (later phase).

## Rules

* The shell (`src/ui/`) never contains plugin-specific logic; a plugin never controls the shell. Plugin UI lives in `plugins/<name>/ui/`, business logic in `plugins/<name>/services/` (no Qt there). Code shared by several plugins (like the SAP connection) lives in `src/core/`.
* Do not remove or rename `main()`, `ping_app()` and `ask_update()` without updating the launcher contract (`ping_app()` is the post-update self-check; it must work without a display). Changes to `docs/contract.md` or `launcher.py` break installed copies and need a new Setup (and a higher `BOOTSTRAP_VERSION` / `min_bootstrap_version`).
* The version number lives in `src/version.py` only (plus `pyproject.toml`, checked by `build.py`). It is always the value written in the project files, unless the user explicitly says otherwise. Do not type it anywhere else. Every release gets an entry in `src/release_notes.json` (for users) and in the change log below (for developers). Dates already written in the change log are never changed.
* Create planned files only when they are actually implemented. Every package folder needs an `__init__.py`, otherwise `pyproject.toml` (`packages.find include = ["src*"]`) skips it.
* Always use the project runtime; `python` / `py` may not exist globally.
* Tests of a plugin live in `tests/<plugin name>/`; tests of shell services in `tests/core/`; tests of the launcher in `tests/bootstrap/`. The user prefers to test Auto Design in the app himself and give feedback: do not write new tests unless he asks.
* **Working with Claude (project instructions):** after changing any code, state which file changed and its exact folder location. If a project file that is needed is not among the provided references (for example `home_page.py`, `main_window.py`, `widgets.py`, `registry.py`), say so before guessing. Say clearly what was written but not run.
* **DCR means the stress ratio** everywhere it is shown (run page, final card, typing page); the governing ratio (stress / deflection) is only used inside `fitness_calculator` for CV (agreed 2026-11-09).
* Auto Design: the GA only talks to the SAP model through small functions (`fitness_calculator`, `SapClient` methods) so the engine can be replaced later (surrogate); every evaluation should end up stored (see the project plan, `core/storage.py` is a stub); the reference file chosen by the user is never modified or saved; the Design Combos of the user's file are never changed.
